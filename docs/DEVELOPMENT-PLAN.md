# 国行电视应用商店 — 开发计划

**版本：** V1.1（阶段 4、5 合并，后续阶段重新编号）

## 开发原则
采用标准 AI Vibe Coding 流程：先规划、再实现；先验证、再扩展；每次只做一个可检查的小任务。不允许一次性生成整个项目。

## 阶段 0：项目初始化
目标：建立规范、干净、可编译的工程。
- 创建项目目录。
- 保存 PRD、TDD、UI-DESIGN。
- 创建 AGENTS.md。
- 创建 README.md 和 CHANGELOG.md。
- 初始化 Git。
- 检查 Windows 开发环境。
- 创建 Android Studio 工程。
- 验证空工程能够编译。

验收：工程结构正确，文档齐全，Git 可用，Android 工程编译成功。

## 阶段 1：电视端 UI 原型
目标：在 TCL Q10L 上看到商店首页。
- 创建 Compose for TV 基础界面。
- 实现顶部横向导航。
- 实现精选应用区域。
- 实现横向应用列表。
- 实现遥控器焦点效果。
- 实现基本页面跳转。

首期使用本地假数据，只验证 UI，不接入服务器。
验收：能够通过遥控器完成首页基本操作，视觉符合 UI-DESIGN.md。

## 阶段 2：APK 安装验证
目标：验证电视端调用系统安装程序。
- 实现文件访问。
- 检查普通 APK。
- 调用 PackageInstaller。
- 获取安装结果。
- 处理取消、失败和签名冲突。

验收：在 TCL Q10L 上成功完成普通 APK 安装测试。

## 阶段 3：下载管理
目标：建立可靠下载模块。
- 创建下载任务。
- 显示进度和速度。
- 暂停和继续。
- 删除任务。
- 失败重试。
- SHA-256 校验。
- HTTP Range 断点续传。
- 重启恢复测试。

验收：电脑端自动化测试（MockWebServer 模拟 Range 续传、校验失败、重启恢复）全部通过；实机验证并入阶段 4 完成后的里程碑测试 1。

## 阶段 4：服务端与管理后台（原阶段 4、5 合并）
目标：建立应用数据服务和管理后台，电视端改为读取真实接口。技术方案以 TDD.md（V1.1）为准。

服务端（`server/`，Laravel 13 + PHP 8.4 + SQLite）：
- 初始化 Laravel 项目，配置 SQLite。
- 建立数据表和迁移：categories、apps、app_versions（含兼容状态、测试设备说明、已知问题、发布状态 草稿/已发布/已撤回）、feedback、users。不建下载统计表。
- 实现 `GET /api/v1/catalog`：返回分类、已上架应用及各自当前发布的版本，支持 ETag，带 If-None-Match 且未变化时返回 304。
- 实现 `GET /api/v1/client/version`：返回商店客户端当前发布的版本。
- 实现 `POST /api/v1/feedback`：无需登录，参数校验，按 IP 限制频率。
- 统一错误响应格式（422、429、500）。
- 用纯 PHP 实现 APK 信息识别：包名、versionName、versionCode、最低 SDK、CPU ABI、签名证书 SHA-256，并计算文件 SHA-256；不依赖 Java、aapt2 或 apksigner。
- 上传规则：包名必须与应用一致，签名必须与已发布过的版本一致，versionCode 不得低于已发布版本，同一应用同一 versionCode 只能有一条记录；每个应用同时最多一个已发布版本。

管理后台（Filament 5，与服务端同一项目）：
- 管理员登录（不开放注册）。
- 分类管理、应用管理（资料、分类、精选、排序、上下架）。
- 版本管理：上传 APK 后自动识别信息，填写兼容状态和已知问题，发布和撤回。
- 反馈查看：修改处理状态、记录处理说明。

电视端：
- 从 `/api/v1/catalog` 读取目录并缓存，替换本地示例数据；网络失败时显示上次缓存的目录，没有缓存时显示错误提示和重试。
- 首页分组、分类和搜索在电视端基于目录数据完成。
- 详情页下载使用接口返回的 downloadUrl、文件大小和 SHA-256。

部署：
- 编写 1Panel 部署说明：创建 PHP 8.4 运行环境和网站、所需 PHP 扩展、HTTPS 证书、网站根目录指向 `public/`、安装包目录由 OpenResty 直接提供静态下载并支持 Range、SQLite 数据库文件和安装包的备份。

验收：
1. 三个接口的 PHPUnit 自动化测试通过（含 ETag/304、反馈参数校验和限频、只返回已上架应用和已发布版本）。
2. APK 识别有自动化测试，覆盖正常安装包、损坏文件和上传规则拒绝的情况。
3. 管理员能够在后台完成分类、应用、版本从上传到发布和撤回的流程，并查看反馈。
4. 电视端读取接口和缓存的自动化测试通过（MockWebServer 模拟接口、304、网络失败），`testDebugUnitTest lintDebug assembleInternal` 通过。
5. 部署说明完成，服务已部署到用户的 1Panel 服务器并可通过 HTTPS 访问。

**里程碑测试 1（阶段 4 完成后）：** 电视端连接用户 1Panel 上的测试服务器，在 TCL Q10L 上验证目录显示、真实下载、校验、续传和安装，并核实通过本商店安装的应用能否被查询（软件包可见性）。由用户实机执行：internal 版 APK 经 115 网盘传到手机，再通过多屏互动安装到电视。不使用 ADB。

## 阶段 5：完整联调（原阶段 6）
目标：形成可实际使用的应用商店。
- 电视端连接正式 API。
- 展示真实应用数据。
- 下载真实安装包。
- 安装应用。
- 检查本商店应用更新和商店客户端自身更新（`/api/v1/client/version`）。
- 电视端提交用户反馈，后台处理反馈。
- 进行兼容性和安全测试。

验收：核心用户流程在 TCL Q10L 上完整通过。

**里程碑测试 2（阶段 5 完成后）：** 由用户在 TCL Q10L 上执行完整流程测试，安装方式同里程碑测试 1，不使用 ADB。

## AI 编程执行规范
每项任务必须：
1. 阅读相关项目文档。
2. 检查现有代码。
3. 给出简短实施计划。
4. 只修改必要文件。
5. 执行构建或测试。
6. 阶段完成并自测通过后提交 Git 并统一汇报。
7. 遇到需要用户决策、批准或实机测试的事项时停止等待；否则在已确认的阶段内连续推进。

## 版本管理
每完成一个可验证阶段，检查 Git 差异并提交。
建议提交节点：初始化工程、首页 UI 完成、遥控器导航完成、APK 安装完成、下载管理完成、服务端与管理后台完成、完整联调完成。

## 测试节奏
日常开发以电脑端自动化测试为准，不要求每个阶段都在电视上测试。TCL Q10L 实机测试只在两个里程碑进行：阶段 4 服务端与管理后台完成后（里程碑测试 1）和阶段 5 完整联调完成后（里程碑测试 2）。实机安装由用户经 115 网盘传到手机、再通过多屏互动安装到电视。不通过 ADB 连接 TCL Q10L。
